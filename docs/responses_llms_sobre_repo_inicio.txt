
```json
{
  "id": "sha256:8dc4...",
  "path": "resources/_lake/Creswell_Creswell-Research_Design-6ed_2022.epub",
  "media_type": "application/epub+zip",
  "title": "Research Design",
```

**arquivo físico → hash → registro → metadados → derivados → projetos que utilizam esse material.**

# 5. PDFs: PyMuPDF primeiro

Para seu projeto, **PyMuPDF é obrigatório na minha opinião**.

A documentação atual mostra extração de texto diretamente do PDF e também suporte a outros formatos, incluindo EPUB. ([PyMuPDF][2])

Instalação:

```powershell
uv add pymupdf pymupdf4llm
```

O `pymupdf4llm` é particularmente interessante porque transforma PDFs em Markdown:

```python
import pymupdf4llm

markdown = pymupdf4llm.to_markdown("document.pdf")
```

e também consegue produzir JSON com informações de layout. ([PyMuPDF][3])

Isso é muito mais útil para pesquisa do que simplesmente:

```python
page.get_text()
```

porque você quer preservar:

```text
título
seções
subseções
listas
tabelas
código
figuras
ordem de leitura
```

# 6. Docling: sim, mas como segunda camada

Eu colocaria:

```powershell
uv add --group documents docling
```

e não faria dele o primeiro extrator.

O Docling atualmente trabalha com PDF e EPUB, entre muitos outros formatos, e pode exportar Markdown, JSON, texto, chunks etc. ([GitHub][4])

A arquitetura seria:

```text
                  ┌── PyMuPDF ──────── rápido
PDF/EPUB ─────────┤
                  └── Docling ──────── estrutura/layout complexo
```

Por exemplo:

```text
extract
   │
   ├── simples → PyMuPDF4LLM
   │
   ├── tabelas/layout → Docling
   │
   └── OCR necessário → pipeline específico
```

Eu **não colocaria OCR pesado como padrão**. O caminho normal deveria ser texto nativo primeiro.

# 7. Metadata: não dependa de uma única fonte

Aqui eu faria um sistema de provedores:

```text
bibliography/
├── zotero.py
├── crossref.py
├── openalex.py
└── semanticscholar.py
```

A ordem poderia ser:

```text
DOI
 ↓
Crossref
 ↓
OpenAlex
 ↓
Semantic Scholar
 ↓
Zotero
 ↓
ISBN/título/autor
 ↓
metadado manual
```

O Crossref possui uma API REST pública para metadados bibliográficos, com busca por DOI e outras consultas. ([www.crossref.org][5])

Semantic Scholar também disponibiliza uma API para dados de artigos, autores, referências e citações. ([Semantic Scholar][6])

A ideia é **não espalhar chamadas HTTP pelo projeto inteiro**. Tudo passa por:

```python
MetadataProvider
```

Assim você pode trocar ou adicionar fontes sem reescrever o resto do sistema.

# 8. Zotero + Better BibTeX

Aqui eu faria uma pequena mudança conceitual.

Não faria seu Python tentar substituir o Zotero.

Faria:

```text
Zotero
   │
   ├── metadados bibliográficos
   ├── coleções
   └── citações
        ↓
Better BibTeX
        ↓
library.bib
        ↓
LaTeX
```

O Zotero atualmente tem API v3 recomendada e também oferece uma API local no cliente desktop, inclusive para leituras sem autenticação. ([Zotero][7])

O Better BibTeX pode manter uma exportação atualizada automaticamente sempre que a biblioteca/coleção mudar. ([Retorque][8])

Eu deixaria o **Zotero como fonte de verdade bibliográfica**.

Seu Python seria consumidor:

```text
Zotero → BBT → BibLaTeX → ACC-PKM
```

e não:

```text
ACC-PKM tentando virar um segundo Zotero
```

Essa última opção é exatamente o tipo de projeto que começa com "vou só automatizar a bibliografia" e termina às 3h da manhã implementando um clone do Zotero.

# 19. GitHub deveria compilar automaticamente

Eu colocaria um CI que faça pelo menos:

```text
push / pull request
        │
        ├── Ruff
        ├── ty
        ├── pytest
        │
        └── LaTeX
              ├── LuaLaTeX
              └── Biber
```

A Action `xu-cheng/latex-action` atualmente compila documentos usando TeX Live e oferece suporte a pdfLaTeX, XeLaTeX e LuaLaTeX; a versão 4 está disponível atualmente. ([GitHub][13])

Um workflow básico:

```yaml
name: LaTeX

on:
  push:
    paths:
      - "projects/**/*.tex"
      - "projects/**/*.bib"
      - "templates/**/*.tex"
  pull_request:
    paths:
      - "projects/**/*.tex"
      - "projects/**/*.bib"
      - "templates/**/*.tex"

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v6

      - name: Build manuscript
        uses: xu-cheng/latex-action@v4
        with:
          root_file: projects/projeto-001/manuscript/main.tex
          latexmk_use_lualatex: true
```

O GitHub também documenta workflows específicos para projetos Python e recomenda `setup-python` para selecionar explicitamente a versão do Python em CI. ([GitHub Docs][14])

# 22. Uma regra importante para os derivados

Nunca faça:

```text
PDF
 ↓
LLM
 ↓
texto "melhorado"
 ↓
substitui PDF original
```

Faça:

```text
PDF original
    │
    ├── extração literal
    │
    ├── interpretação estrutural
    │
    ├── enriquecimento
    │
    └── análise por IA
```

Cada camada permanece separada.

Por exemplo:

```text
_derived/
├── markdown/
│   └── 8dc4...md
├── json/
│   └── 8dc4...json
├── ai/
│   └── 8dc4...analysis.json
└── provenance/
    └── 8dc4...json
```

A IA pode sugerir:

```text
tema
método
conceitos
resumo
relações
```

### 3. Integração LaTeX: VS Code, GitHub e Overleaf

#### VS Code

* **LaTeX Workshop:** Extensão padrão. Configure a receita de compilação para `latexmk` com `-synctex=1 -interaction=nonstopmode -file-line-error -pdf -outdir=build`. Guardar saídas na pasta `build/` evita sujar o repositório com `.aux`, `.log`, `.fls`.
* **LTeX+ (LanguageTool):** Verificador gramatical multilíngue no próprio editor. Suporta alternar facilmente entre Português e Inglês no mesmo documento acadêmico e ignora comandos de controle do LaTeX.

#### GitHub Actions

Adicione um workflow simples em `.github/workflows/compile-latex.yml` para compilar os documentos da pasta `projects/` a cada push ou pull request, anexando os PDFs gerados como artefatos de release ou build:

```yaml
name: Compile LaTeX Documents
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Compile LaTeX
        uses: xu-cheng/latex-action@v3
        with:
          root_file: main.tex
          working_directory: projects/2026_artigo_evento
      - uses: actions/upload-artifact@v4
        with:
          name: artigo-pdf
          path: projects/2026_artigo_evento/main.pdf

```

#### O gargalo do Overleaf com Monorepos

O Overleaf sincroniza o repositório Git esperando que o documento principal (`main.tex`) esteja na raiz ou seja facilmente identificável. Ele não lida de forma nativa com pastas aninhadas complexas de monorepos.

Três soluções viáveis:

1. **Git Subtree / Submodules:** Cada artigo em `projects/nome_do_artigo` pode ser um submódulo ou sincronizado via `git subtree` com um repositório isolado espelhado no Overleaf.
2. **Script de Sync via GitHub Action:** Um workflow acionado quando você edita a pasta do projeto específico, dando push apenas daquela pasta para o repositório privado do Overleaf.
3. **Desenvolvimento Híbrido:** Escrever e formatar a versão final localmente no VS Code, usando o Overleaf pontualmente apenas quando houver coautores que não usam Git/VS Code (subindo um ZIP ou pasta isolada).

- Catálogo automatizado de PDFs e EPUBs.
- GitHub Actions para qualidade e compilação LaTeX.
- Bibliotecas recomendadas por finalidade.
- Plano de implantação em quatro fases.

O primeiro marco prático deve ser: **clonar → `uv sync` → verificar qualidade → gerar catálogo → compilar um manuscrito LaTeX**, tudo por comandos reproduzíveis. O relatório contém os exemplos de configuração e a sequência detalhada para chegar a esse ponto.


# Arquitetura enxuta para um monorepo de pesquisa acadêmica

## Recomendação central

A melhor base para o estágio atual é **um único repositório de conteúdo, com um único pacote Python de automação na raiz**, e não um workspace UV com vários pacotes. O UV já oferece ambiente isolado, `pyproject.toml`, grupos de dependências e um `uv.lock` reproduzível; workspaces passam a valer a pena somente quando existirem vários pacotes Python internos com ciclos de vida próprios, pois cada membro ganha seu `pyproject.toml`, mas todos compartilham o mesmo lockfile.[1][2][3]

O repositório deve separar quatro coisas que hoje estão misturadas conceitualmente: **fontes bibliográficas**, **projetos de pesquisa**, **conhecimento reutilizável** e **automação**. O Git deve versionar textos, código, metadados e configurações; o Git LFS deve guardar apenas os binários necessários; PDFs compilados e índices HTML devem ser tratados como produtos gerados, não como fontes.

## O que versionar

| Categoria | Destino | Git comum | Git LFS | Ignorar |
|---|---|---:|---:|---:|
| LaTeX, Markdown, BibLaTeX, YAML e código | Pastas de projeto e raiz | Sim | Não | Não |
| PDFs e EPUBs-fonte | `resources/_lake/` | Não | Sim | Não |
| Dados brutos grandes e permitidos | `projects/*/data/raw/` | Não | Sim | Conforme licença |
| CSVs pequenos e tabelas finais | `data/processed/` ou `tables/` | Sim | Não | Não |
| PDF compilado, auxiliares LaTeX e HTML de catálogo | `outputs/`, `build/`, `_lake_catalog.html` | Não | Não | Sim |
| Ambientes e caches | `.venv/`, `.cache/`, `.pytest_cache/` | Não | Não | Sim |
| Índice local de busca em texto integral | `.local/` | Não | Não | Sim |

O Git LFS deixa no histórico Git apenas ponteiros e armazena os binários separadamente. Entretanto, cada alteração em um binário envia uma nova cópia completa e conta novamente para o uso de armazenamento; por isso, o `_lake` deve ser tratado como **imutável**: adicionar, deduplicar e, quando necessário, substituir conscientemente, mas nunca editar EPUBs e PDFs repetidamente.[4][5]

Como o acervo mostrado contém livros provavelmente protegidos por direitos autorais, a opção prudente é manter o repositório privado e não incluir `resources/_lake/` em releases, Zenodo, GitHub Pages ou exportações para Overleaf. Metadados, fichamentos autorais e referências podem ser publicados separadamente quando desejado.

## Bootstrap no Windows

Na raiz atual, o primeiro bootstrap pode ser feito no PowerShell:

```powershell
git init
git branch -M main

git lfs install
git lfs track "resources/_lake/*.pdf"
git lfs track "resources/_lake/*.epub"

uv init --package --python 3.12
uv add typer rich pydantic pyyaml httpx pymupdf ebooklib bibtexparser python-slugify
uv add --group dev ruff pytest pytest-cov pre-commit poethepoet
uv add --group data jupyterlab duckdb pandas polars pyarrow matplotlib
uv add --group nlp spacy

uv sync
uv run pre-commit install
```

Os comandos `uv add --group` registram dependências locais em grupos independentes, que não fazem parte de um pacote publicado. O UV mantém versões exatas em `uv.lock`; `uv sync` sincroniza o ambiente e, em CI, `uv sync --locked` deve falhar se o lockfile não corresponder ao `pyproject.toml`, em vez de alterá-lo silenciosamente.[6][7][1]

Não é necessário instalar todos os grupos sempre. O uso diário pode manter apenas `dev`; um notebook analítico pode usar `uv sync --group data`, e um projeto de NLP pode acrescentar `--group nlp`. Isso reduz o ambiente padrão sem impedir expansões temáticas.

## Configuração do UV

Após os comandos de bootstrap, estas seções podem ser incorporadas ao `pyproject.toml` gerado pelo UV:

```toml
[project]
name = "acc-pkm"
version = "0.1.0"
description = "Monorepo acadêmico e ferramentas para pesquisa reproduzível"
requires-python = ">=3.12"

[project.scripts]
acc-pkm = "acc_pkm.cli:app"

[tool.uv]
default-groups = ["dev"]

[tool.ruff]
target-version = "py312"
line-length = 100
extend-exclude = [
  "resources/_lake",
  "projects/*/outputs",
  "projects/*/data/raw",
]

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP", "SIM"]

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q"

[tool.poe.tasks]
lint = "ruff check ."
format = "ruff format ."
format-check = "ruff format --check ."
test = "pytest"

[tool.poe.tasks.check]
sequence = ["lint", "format-check", "test"]
```

O Ruff cobre lint, organização de imports e formatação em uma ferramenta; a documentação recomenda executar correções de lint/imports antes do formatador. O `pytest` descobre por padrão arquivos `test_*.py` e `*_test.py`, o que combina com uma pasta central de testes para catálogo, templates e comandos. O Poe the Poet funciona com ambientes gerenciados pelo UV e permite declarar tarefas documentadas diretamente no `pyproject.toml`, evitando scripts PowerShell e Bash duplicados.[8][9][10][11][12][13]

Com isso, os comandos humanos ficam estáveis:

```powershell
uv run poe format
uv run poe check
uv run acc-pkm catalog scan
uv run acc-pkm catalog render
uv run acc-pkm project new "titulo-do-projeto"
uv run acc-pkm refs sync "titulo-do-projeto"
```

Os quatro comandos `acc-pkm` são o primeiro pequeno produto de automação a implementar; não é necessário criar dezenas de abstrações antes de o fluxo real mostrar quais se repetem.

## Catálogo do acervo

O arquivo `_lake_catalog.html` atual deve passar a ser **saída gerada**. A fonte canônica deve ser `resources/catalog/library.csv` ou, se os registros crescerem e ganharem campos compostos, `library.jsonl`; ambos são legíveis por Git, Python, DuckDB e planilhas.

O catálogo mínimo deve registrar:

- `resource_id`: identificador estável, preferencialmente prefixo do SHA-256.
- `path`: caminho relativo dentro do repositório.
- `sha256`: deduplicação e verificação de integridade.
- `media_type`, `bytes` e `pages`.
- `title`, `authors`, `year`, `edition` e `language`.
- `doi`, `isbn` e `source_url`, quando existirem.
- `rights`: `personal-copy`, `open-access`, `public-domain`, `unknown` etc.
- `tags`, `status`, `added_at` e `notes`.
- `extraction_status`: indica se metadados vieram do arquivo, de API ou de revisão manual.

A rotina `catalog scan` deve calcular hashes, detectar duplicatas, extrair metadados básicos com PyMuPDF/EPUBLib e preservar correções humanas já existentes. `catalog render` deve produzir o HTML navegável. Para artigos científicos, GROBID pode ser acrescentado depois como serviço Docker: ele transforma PDFs acadêmicos em TEI/XML estruturado e extrai cabeçalho, referências, contextos de citação, seções, figuras e tabelas.[14][15]

Não convém colocar texto integral extraído no Git. Para busca local, uma etapa opcional pode gerar `resources/.local/search.duckdb`, ignorado pelo Git, contendo texto e embeddings reconstruíveis a partir dos arquivos que o usuário já possui legalmente.

## Bibliografia e citações

A pilha recomendada é **Zotero + Better BibTeX + `references/library.bib`**. O Better BibTeX oferece chaves de citação estáveis, exportação automática de coleções e integração com fluxos LaTeX/Markdown.[16][17]

Fluxo sugerido:

1. Importar e corrigir a referência no Zotero.
2. Criar coleções por projeto ou tema.
3. Configurar uma autoexportação Better BibLaTeX da biblioteca para `references/library.bib`.
4. Fixar chaves importantes para evitar mudanças após o manuscrito começar.
5. Fazer `acc-pkm refs sync <projeto>` copiar apenas as entradas citadas ou pertencentes à coleção para `projects/<projeto>/manuscript/references.bib`.

O arquivo por projeto facilita o envio ao Overleaf e torna cada manuscrito autocontido. A biblioteca global continua sendo a fonte bibliográfica principal; o arquivo local é um recorte gerado e deve trazer no cabeçalho um aviso para não ser editado manualmente.

Para documentos Markdown ou Quarto, o Pandoc processa referências com `--citeproc`, recebe bibliografia externa e aplica estilos CSL; isso permite reutilizar o mesmo `.bib` para HTML, DOCX e PDF. Quarto é uma camada opcional valiosa para relatórios com notebooks, equações, tabelas, referências cruzadas e citações, mas não precisa substituir LaTeX em artigos cuja formatação final depende de classes de periódicos.[18][19][20][21]

## LaTeX no VS Code

No Windows, a combinação mais previsível é **TeX Live + LaTeX Workshop + latexmk**. O TeX Live inclui Perl e normalmente inclui `latexmk`; a receita padrão do LaTeX Workshop usa `latexmk`, que executa a sequência necessária de compiladores e ferramentas bibliográficas.[22][23]

Extensões iniciais do VS Code:

```json
{
  "recommendations": [
    "James-Yu.latex-workshop",
    "astral-sh.ty",
    "charliermarsh.ruff",
    "ms-python.python",
    "ms-toolsai.jupyter",
    "quarto.quarto",
    "redhat.vscode-yaml",
    "tamasfe.even-better-toml",
    "yzhang.markdown-all-in-one"
  ]
}
```

Configuração enxuta em `.vscode/settings.json`:

```json
{
  "python.defaultInterpreterPath": "${workspaceFolder}\\.venv\\Scripts\\python.exe",
  "python.terminal.activateEnvironment": true,
  "ruff.nativeServer": "on",
  "editor.formatOnSave": true,
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff"
  },
  "latex-workshop.latex.autoBuild.run": "onSave",
  "latex-workshop.latex.outDir": "%DIR%/../outputs/build",
  "latex-workshop.view.pdf.viewer": "tab",
  "files.exclude": {
    "**/.venv": true,
    "**/__pycache__": true,
    "**/outputs/build": true
  }
}
```

O LaTeX Workshop permite escolher receitas e usa `latexmk` por padrão; o build no salvamento também é uma configuração suportada. ChkTeX pode ser ativado mais tarde como linter semântico de LaTeX; ele detecta problemas tipográficos que o compilador não trata como erros, mas deve ser configurado para evitar excesso de avisos.[23][24][25][26]

## Template de projeto

Cada pesquisa deve começar com um `project.yml` simples:

```yaml
id: example-study
title: Título provisório
type: empirical-study
status: idea
language: pt-BR
created: 2026-09-29
updated: 2026-09-29
owners:
  - Vitor R. Santos
research_questions:
  - Qual é a pergunta principal?
keywords: []
methods: []
bibliography: manuscript/references.bib
entrypoint: manuscript/main.tex
```

O comando `acc-pkm project new` deve validar o slug, copiar `templates/article/`, preencher data e título e recusar sobrescrita. Os tipos iniciais suficientes são `article`, `systematic-review` e `research-note`; novos templates só devem ser criados quando houver diferença estrutural real.

Para revisões sistemáticas, o mesmo diretório pode ganhar `protocol/`, `screening/` e `extraction/`, com CSVs de decisões e critérios versionados. Para experimentos, `notebooks/` serve à exploração, mas resultados finais devem migrar para funções em `scripts/` ou `src/`, cobertas por testes e executáveis de forma determinística.

## Git LFS com disciplina

A `.gitattributes` deve ser gerada pelos comandos `git lfs track` e mantida no Git. É preferível restringir o LFS aos diretórios de acervo e dados brutos, em vez de rastrear `*.pdf` globalmente, porque PDFs de manuscritos são produtos de build e não devem entrar no histórico.

Uma política útil é:

```gitattributes
resources/_lake/*.pdf filter=lfs diff=lfs merge=lfs -text
resources/_lake/*.epub filter=lfs diff=lfs merge=lfs -text
projects/*/data/raw/*.zip filter=lfs diff=lfs merge=lfs -text
projects/*/data/raw/*.parquet filter=lfs diff=lfs merge=lfs -text
```

Antes do primeiro push, execute:

```powershell
git lfs ls-files
git check-attr -a resources/_lake/arquivo.pdf
git status
```

O plano do GitHub inclui franquias de armazenamento e download para LFS, e o comportamento ao ultrapassá-las depende do plano, do método de pagamento e do orçamento configurado. Como versões completas de binários se acumulam, o catálogo deve mostrar tamanho e duplicatas antes do commit.[27][4]

## Pre-commit

A primeira configuração deve ser curta: remover espaços finais, garantir newline final, validar YAML/TOML/JSON, detectar marcadores de conflito, bloquear arquivos grandes fora do LFS e rodar Ruff. O framework instala hooks locais com `pre-commit install`, pode executar tudo com `pre-commit run --all-files` e atualizar versões fixadas com `pre-commit autoupdate`.[28]

O hook `check-added-large-files` permite definir o tamanho máximo aceito no Git normal; combinado com o LFS, ele impede que um PDF seja adicionado por engano sem o filtro correto. A recomendação é começar com limite de 2 MB para arquivos não-LFS e abrir exceções explícitas apenas para pequenos recursos realmente textuais ou necessários.[29]

## GitHub Actions

A automação inicial precisa de apenas dois workflows.

### Qualidade Python

```yaml
name: quality

on:
  pull_request:
  push:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: false
      - uses: astral-sh/setup-uv@v6
        with:
          enable-cache: true
      - run: uv sync --locked --group dev
      - run: uv run poe check
```

O checkout deve manter `lfs: false` para que lint e testes não baixem todo o acervo. A integração oficial do UV para GitHub Actions recomenda `astral-sh/setup-uv`, `uv sync --locked` e execução de ferramentas via `uv run`; a action também oferece cache baseado em arquivos como `uv.lock` e `pyproject.toml`.[30][31]

### Compilação LaTeX

```yaml
name: latex

on:
  pull_request:
    paths:
      - "projects/**/*.tex"
      - "projects/**/*.bib"
      - ".github/workflows/latex.yml"

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: false
      - uses: xu-cheng/latex-action@v4
        with:
          root_file: main.tex
          working_directory: projects/example-study/manuscript
      - uses: actions/upload-artifact@v4
        with:
          name: example-study-pdf
          path: projects/example-study/manuscript/main.pdf
          retention-days: 14
```

A LaTeX Action usa uma imagem com TeX Live completo e `latexmk` como compilador padrão. Artifacts permitem guardar o PDF produzido pelo workflow sem versioná-lo no repositório e aceitam prazo de retenção configurável. Quando houver vários manuscritos ativos, o job pode virar uma matriz explícita; geração dinâmica de matriz deve esperar até existir necessidade real.[32][33][34][35]

## Overleaf sem conflito

Overleaf deve ser tratado como **editor colaborativo de um manuscrito**, não como espelho do monorepo. Exporte apenas `projects/<slug>/manuscript/`, suas figuras necessárias e o `references.bib` específico; nunca envie `_lake`, ambientes Python ou dados brutos.

A sincronização direta do Overleaf com GitHub exige vinculação de conta, não é automática e não permite simplesmente ligar dois projetos já existentes; a documentação também recomenda menos de 100 arquivos por commit e projeto abaixo de 100 MB para esse fluxo. A integração Git, disponível como recurso premium, permite adicionar o Overleaf como segundo remote do projeto local e fazer `push`/`pull` explicitamente.[36][37][38]

Para evitar conflitos, escolha um dono operacional por manuscrito em cada período: ou as edições entram principalmente pelo GitHub/VS Code, ou principalmente pelo Overleaf. Sincronizações bidirecionais simultâneas sem coordenação criam merges desnecessários.

## Descoberta bibliográfica

A automação de busca deve começar por metadados, não por scraping de páginas. Crossref permite acesso público e recomenda fornecer e-mail em `mailto` e identificar o cliente no `User-Agent`; isso melhora a etiqueta operacional e permite contato em caso de problema. OpenAlex oferece endpoints para obras, autores, fontes, instituições e tópicos, com busca, filtros, ordenação e paginação; identificadores como DOI, ORCID e OpenAlex ID são preferíveis a nomes ambíguos.[39][40][41]

Um comando futuro `acc-pkm discover` pode:

- Receber consulta, intervalo de anos, tipo documental e filtros de acesso aberto.
- Consultar Crossref e OpenAlex com cache local.
- Normalizar DOI, título, autores, ano, fonte e resumo.
- Deduplicar por DOI e, subsidiariamente, por título normalizado.
- Exportar CSV para triagem e BibLaTeX para Zotero.
- Registrar consulta, data, parâmetros, total retornado e versão do código para reprodutibilidade.

A busca OpenAlex cobre título, resumo e parte do texto integral, e aceita operadores booleanos e frases exatas. Resultados ainda precisam de triagem humana; APIs ajudam na recuperação e documentação, não substituem avaliação metodológica.[42]

| PDFs e EPUBs | PyMuPDF, EPUBLib | Catálogo e extração local | Agora |

Evite instalar “tudo de ciência de dados” no grupo padrão. Cada nova dependência deve responder a uma tarefa concreta, entrar no grupo correto e ser fixada pelo `uv.lock`.

## Convenções importantes

- Use nomes de pastas em `kebab-case`, módulos Python em `snake_case` e chaves bibliográficas estáveis.
- Datas em metadados devem usar ISO 8601, por exemplo `2026-09-29`.
- Caminhos gravados em CSV/YAML devem ser relativos e usar `/`, mesmo no Windows.
- Dados brutos são imutáveis; transformação gera `interim` e `processed`.
- Toda figura final deve ter um script ou notebook-fonte identificável.
- Notebooks não devem ser a única implementação de uma análise crítica.
- Segredos e tokens ficam em `.env`, nunca no Git; publique apenas `.env.example`.
- O catálogo e os PDFs compilados devem ser reconstruíveis por comando.
- Commits devem separar acervo, código, análise e manuscrito quando possível.

## Fases de implantação

### Fase 1: fundação

1. Inicializar Git, UV e Git LFS.
2. Mover o catálogo HTML para saída gerada e criar `library.csv`.
3. Criar `src/acc_pkm`, `tests`, `projects`, `notes`, `references` e `templates`.
4. Configurar Ruff, pytest, Poe e pre-commit.
5. Adicionar configurações do VS Code e um template LaTeX mínimo.
6. Criar o workflow `quality.yml`.

### Fase 2: automação útil

1. Implementar `catalog scan` e `catalog render`.
2. Implementar `project new`.
3. Configurar Zotero/Better BibTeX e `refs sync`.
4. Adicionar testes de deduplicação, preservação de metadados e geração de projetos.
5. Criar o workflow LaTeX para o primeiro manuscrito real.

### Fase 3: pesquisa reproduzível

1. Adicionar busca Crossref/OpenAlex com cache e registro de consultas.
2. Criar schemas para protocolos, triagem e extração de dados.
3. Adotar Quarto apenas onde houver narrativa computacional.
4. Adicionar GROBID quando o volume de artigos justificar o serviço.
5. Criar releases de código e templates; não incluir o acervo privado.

### Fase 4: publicação

Quando o código estiver maduro e publicável, `CITATION.cff` informa ao GitHub como citar o repositório e ativa o bloco “Cite this repository” na página do projeto. Se o repositório público for integrado ao Zenodo, cada release pode ser arquivado com um DOI; essa integração deve ser usada apenas em uma versão limpa, sem materiais de terceiros que não possam ser redistribuídos.[43][44][45][46]

## Decisões que devem esperar

Não crie agora um UV workspace, um banco vetorial compartilhado, microserviços, uma ontologia complexa de notas ou sincronização automática bidirecional com Overleaf. Essas soluções podem ser úteis, mas aumentam o custo antes de existir demanda comprovada.

## 2. Setup com uv

```powershell
cd acc_pkm
uv init --package
uv python pin 3.12
uv add --group research pymupdf pyalex arxiv habanero semanticscholar bibtexparser pyzotero
uv add --group analysis pandas polars statsmodels pingouin scikit-learn matplotlib seaborn
uv add --group slr asreview
uv add --group dev ruff pytest mypy poethepoet
```

> Gotcha: `uv sync` instala só o grupo `dev` por padrão. Use `uv sync --all-groups`.

No `pyproject.toml`, adicione tasks:

```toml
[tool.poe.tasks]
catalog = "python scripts/catalog.py"   # regenera catálogo do _lake
dig     = "python scripts/dig.py"       # busca artigos em várias fontes
new     = "python scripts/new_paper.py" # scaffold de novo paper a partir de _template
```

Roda com `uv run poe catalog`. (`poe` é o `make` multiplataforma — melhor que Makefile no Windows.)

## 4. Bibliografia: o fluxo que recomendo

**Zotero 7 + Better BibTeX**, com o truque que faz tudo funcionar num monorepo:

1. Uma **coleção Zotero por paper** (além da biblioteca geral).
2. No BBT, configure **auto-export**: biblioteca inteira → `references/main.bib`, e cada coleção → `papers/<slug>/refs.bib` — ambos com "Keep updated".
3. Cada paper fica **autocontido** (compila com o próprio `refs.bib`), o que é essencial pro sync com Overleaf depois.

Citation keys no formato `auth_year_firstword` (padrão BBT decente). Para venue brasileira: `abntex2` (classe) e `biblatex-abnt` (citações ABNT).

Se preferir 100% terminal/repo: `papis` guarda PDFs + `info.yaml` em pastas — daria pra apontar a library pra dentro do repo, mas aí o `_lake` entraria no git (vide alerta). Zotero separa melhor "arquivos" de "repo".

## 7. Overleaf (o ponto delicado)

Repos não aninham bem. Estratégias:

- **Plano grátis**: use `ols` (overleaf-sync, `uv tool install overleaf-sync`) — sincroniza uma pasta local com um projeto Overleaf via API. Monorepo continua sendo a fonte da verdade; você sincroniza só a pasta do paper ativo.
- **Plano pago** (tem git bridge): o projeto Overleaf vira um remote e você usa `git subtree`:

```powershell
git remote add overleaf-foo https://git.overleaf.com/<id>
git subtree pull --prefix=papers/2025-slr-foo overleaf master
git subtree push --prefix=papers/2025-slr-foo overleaf master
```

Por isso o paper autocontido (com `refs.bib` próprio) importa tanto.

## 8. Primeira automação: regenerar o catálogo do lake

Isso substitui seu `_lake_catalog.html` por algo versionável (só metadados):

```python
# scripts/catalog.py
import csv, html
from pathlib import Path
import pymupdf

LAKE = Path("resources/_lake")
OUT = Path("resources/_catalog"); OUT.mkdir(parents=True, exist_ok=True)

rows = []
for f in sorted(LAKE.iterdir()):
    r = {"arquivo": f.name, "titulo": f.stem.replace("_", " "),
         "autores": "", "paginas": "", "mb": round(f.stat().st_size / 1e6, 1)}
    if f.suffix.lower() == ".pdf":
        with pymupdf.open(f) as doc:
            m = doc.metadata or {}
            r["titulo"] = m.get("title") or r["titulo"]
            r["autores"] = m.get("author") or ""
            r["paginas"] = doc.page_count
    rows.append(r)

with open(OUT / "catalog.csv", "w", newline="", encoding="utf-8") as fh:
    w = csv.DictWriter(fh, fieldnames=rows[0].keys()); w.writeheader(); w.writerows(rows)

cards = "\n".join(
    f"<li><b>{html.escape(r['titulo'])}</b> — {r['autores'] or '?'} "
    f"({r['paginas'] or '—'} p., {r['mb']} MB)<br><code>{r['arquivo']}</code></li>"
    for r in rows)
(OUT / "index.html").write_text(
    f"<!doctype html><meta charset='utf-8'><title>Lake</title><ul>{cards}</ul>",
    encoding="utf-8")
print(f"{len(rows)} itens catalogados.")
```

`uv run poe catalog` e pronto. Melhorias futuras: lookup de DOI no Crossref via `habanero` pra enriquecer/normalizar autores.
